# ボンディング回線スループット測定ツール

Peplink ルーター(MAX BR2 Pro / MAX Transit Pro Duo)配下のPCから、
**ボンディングした回線の最大スループットとRTT**を実測するツールです。
オプションで**回線を1本ずつ自動で切り替えて、各回線単体のポテンシャル
(最大スループット・RTT)**も測定できます。

- 多並列HTTP転送で回線を飽和させ、**1秒ピーク**と**定常平均**を算出
- RTTは**無負荷時**と**転送中(負荷時)**の両方を計測 — 差が大きいほど
  バッファブロート(混雑時の遅延悪化)が大きい回線です
- 結果はコンソールの比較表+CSV(履歴追記)+JSONに保存
- `--monitor 2h` で**時間を指定した連続計測(1秒ごとにCSV記録、1時間≒0.2MB)**
- 同梱の **viewer.html** をブラウザで開けば、CSVをグラフ・統計・ズームで確認できる
- **コマンド不要の対話メニュー付き**: 「計測スタート」をダブルクリック(または引数なしで起動)すると、
  番号を選んでEnterを押すだけの日本語メニューが立ち上がります
- [設定管理コンソール](../peplink-console/)/[IC2ロガー](../ic2-logger/)とは独立した別アプリです

## 1. 動作要件

| 項目 | 要件 |
|---|---|
| 実行場所 | **測定対象のPeplinkルーターのLAN配下のPC**(有線接続を推奨。Wi-Fi経由はWi-Fiがボトルネックになります) |
| OS / Python | Windows / macOS / Linux、Python 3.9以上 |
| 追加パッケージ | PyYAML のみ |
| PCの性能 | 1Gbps超を測る場合は有線1GbE以上のNICを推奨 |
| --per-wan 使用時 | ルーターのRouter APIが有効で、Read-Write権限の認証情報があること |

## 2. インストールと最初の測定

### コマンドが苦手な方向け(推奨): ダブルクリックで起動

1. [Python](https://www.python.org/downloads/) をインストール
   (Windowsは「Add Python to PATH」に必ずチェック)
2. このフォルダの **「計測スタート.bat」(Windows)** または
   **「計測スタート.command」(Mac)** をダブルクリック
   ※初回は自動で準備(PyYAMLのインストール)が走ります
   ※Macで「開発元を確認できない」と出たら、右クリック→「開く」
3. 日本語のメニューが表示されるので、**番号を選んでEnterを押すだけ**です

```
  1) かんたん測定 — 今のボンディング回線の速度とRTTを測る(約30秒)
  2) 連続計測 — 時間を決めて1秒ごとにCSVへ記録し続ける
  3) 回線ごとの測定 — 回線を1本ずつ切り替えて各回線の実力を測る
  4) 結果を見る — ビューワー(グラフ画面)をブラウザで開く
  5) 動作確認 — ネットワークを使わずに試してみる(デモ)
  6) 測定先サーバーとして起動 — 本社・拠点側のPCで使う
```

- 迷ったら **そのままEnter**(★印の既定値)で進めます
- 計測時間・データ量の上限などもすべて対話で聞かれます
- 実行前に「これから何をするか・通信量の目安」が必ず表示されます
- 回線ごとの測定で必要なルーター接続情報も対話で入力でき、保存も選べます
- ターミナルから使う場合は `python3 run.py`(引数なし)でも同じメニューが開きます

### コマンドで使う場合

```bash
cd Peplink_BondingRouterSetup/tools/bonding-speedtest
python3 -m pip install -r requirements.txt

python3 run.py --demo      # 動作確認(ネットワークを使わずローカルで完結)
python3 run.py --duration 12 --streams 8   # 引数を付けると対話なしで即実行
```

## 3. 測定の仕組みと結果の見方

| 項目 | 意味 |
|---|---|
| **下り/上り 平均** | 立ち上がり(先頭20%)を除いた定常区間の平均スループット。**実運用で期待できる値** |
| **下り/上り ピーク** | 0.25秒サンプルの1秒間ローリング最大。**瞬間最大値** |
| **RTT(無負荷)** | 転送していない時のTCP接続確立時間(min/avg/p95) |
| **RTT(負荷中)** | 転送で回線が埋まっている最中のRTT。無負荷との差が大きい回線は、映像伝送中に遅延が膨らみやすい(バッファブロート) |
| 使用データ量 | フェーズごとに表示。従量SIMでは要確認 |

- 複数の並列TCPコネクション(既定8本)で転送するため、ボンディング測定では
  Weighted Balance等の負荷分散でも自然に複数WANへ分散します。
- 上りは送信側での計測です(末端の未達分をわずかに含む場合があります)。

### 保存されるファイル(results/)

| ファイル | 内容 |
|---|---|
| `speedtest_summary.csv` | 1フェーズ=1行のサマリ。**実行のたびに追記**され、履歴比較に使える |
| `speedtest_<日時>.json` | その実行の詳細(RTT分布、エラー等) |
| `speedtest_<日時>_samples.csv` | `--samples` 指定時のみ。0.25秒刻みの明細(グラフ化用) |

## 4. 連続計測モード(1秒ごとにCSV記録)

`--monitor <時間>` で、指定した時間にわたって転送とRTTプローブを流し続け、
**1秒ごとに1行**をCSVに記録します。数時間の安定性確認(ソークテスト)向けです。

```bash
python3 run.py --monitor 2h                  # 2時間の連続計測
python3 run.py --monitor 90m                 # 90分
python3 run.py --monitor 1h30m --limit-mb 5000   # 1時間30分・片方向5GBで打ち切り
python3 run.py --monitor 8h --no-download --no-upload   # RTTだけ8時間(データ消費ほぼゼロ)
```

時間の書き方: `2h`(時間)/ `90m`(分)/ `45s`(秒)/ `1h30m` / `3600`(秒)。

### 出力ファイル(1秒 = 1行)

`results/monitor_<開始日時>.csv`:

| 列 | 内容 |
|---|---|
| `time` | 記録時刻 |
| `elapsed_s` | 開始からの経過秒 |
| `down_mbps` / `up_mbps` | その1秒間の下り/上りスループット(Mbps) |
| `rtt_ms` / `rtt_max_ms` | その1秒間のRTT平均/最大(ms) |
| `rtt_fail` | その1秒間に失敗したRTTプローブ数(0以外は疎通異常の兆候) |

**ファイルサイズは1時間あたり約0.2MB**(1行約60バイト×3600行)。
10時間計測しても約2MBで、肥大化しません。行は毎秒書き込み+flushされるため、
途中でPCが落ちてもそこまでのデータは残ります。

終了時にはコンソールへ平均/ピーク/RTT最大/使用データ量のサマリを表示し、
`speedtest_summary.csv` にも1行追記します(バースト測定と同じ履歴に並びます)。

### 注意: データ使用量

連続計測は回線を飽和させ続けるため、**100Mbpsの回線なら1時間あたり約45GB(片方向)**
を消費します。数時間の計測は以下のいずれかを推奨します:

- `--limit-mb` で上限を設定(到達した時点で計測終了)
- `--no-upload`(下りのみ)や `--no-download --no-upload`(RTTのみ=消費ほぼゼロ)
- 自社リフレクター+固定回線側での実施

## 5. 結果ビューワー(viewer.html)

計測後、**`viewer.html` をダブルクリックしてブラウザで開き**、
`results/monitor_*.csv` を読み込むと(クリックして選択 or ドラッグ&ドロップ)、
グラフと統計が表示されます。インストール・サーバー・ネット接続は不要で、
データはブラウザの外に出ません。

表示内容:

- **統計タイル**: 下り/上りの平均・ピーク・p95・使用GB、RTTの平均・p95・最大、
  RTT失敗回数(=疎通異常の兆候)
- **スループットグラフ**(下り/上り)と**RTTグラフ**: 平均線+その区間の最小〜最大の帯。
  長時間データは自動で間引き描画されるので数時間分でも軽快です
- **マウス操作**: ホバーで数値表示 / **ドラッグで範囲ズーム** / ダブルクリックで全体表示。
  ズームすると統計タイルもその範囲で再計算されます(障害時間帯の切り分けに便利)
- **1分ごとの集計表**(下部の折りたたみ)
- 複数CSVを読み込んでプルダウンで切り替え可能(計測日ごとの比較に)

## 6. 回線ごとの測定(--per-wan)

```bash
python3 run.py --per-wan   # またはウィザードの「3) 回線ごとの測定」
```

切り替え方法は2つあり、ウィザードでは選択できます:

| 方式 | 仕組み | 必要なもの |
|---|---|---|
| **自動** | Router APIでWAN優先度を切替→測定→自動復元 | APIの有効化とRead-Write権限 |
| **手動** | 測定のたびに自分でWeb管理画面のダッシュボードで優先度を切替(ツールは測定と記録だけ行う) | **ルーターへのAPI設定は不要** |


各回線単体のポテンシャルを知るために、**ルーターのWAN優先度を一時的に切り替えながら**
順番に測定します。

1. 現在の優先度構成を保存
2. 対象WANだけを優先度1に、他の有効WANは優先度2(待機)に変更(Router APIの即時反映)
3. 対象WANの接続確認 → 安定待ち → 測定
4. すべての回線で繰り返し、**終了後に必ず元の優先度へ復元**(エラー時・Ctrl+C時も復元を試みます)

**重要な注意**:

- 測定中はその回線1本に全通信が乗ります。**本番運用中には実行しないでください**
- 実行前に確認プロンプトが出ます(自動化する場合のみ `--yes`)
- `config.yaml` の `router` セクション(機器IPとRead-Write権限の認証情報)が必要です
- SpeedFusionトンネル経由で通信が出ていく構成の場合、トンネルは独自のWAN優先度を
  持つため単体測定になりません。**単体測定はインターネット直行の測定先
  (既定のCloudflare)で行ってください**
- 万一復元に失敗した場合は、元の優先度が画面に表示されます。Web管理画面の
  ダッシュボードで手動復元してください

## 7. 測定先の選び方(Cloudflare / 自社サーバー)

| 測定先 | 測れるもの | 設定 |
|---|---|---|
| **Cloudflare(既定)** | インターネット直行の回線性能。回線単体のポテンシャル測定に最適 | 設定不要 |
| **自社サーバー(同梱リフレクター)** | **SpeedFusionトンネル越しの実効性能**(実際に映像が通る経路そのもの) | 下記 |

自社サーバー(本社・データセンター側)での準備:

```bash
# 測定先にするサーバーで(ポート8123で待ち受け)
python3 run.py --serve --port 8123
```

測定側の `config.yaml`:

```yaml
targets:
  download_url: http://203.0.113.10:8123/__down?bytes={bytes}
  upload_url: http://203.0.113.10:8123/__up
  rtt_host: 203.0.113.10
  rtt_port: 8123
```

> 経路がトンネルを通るかはルーターのアウトバウンドポリシー次第です。
> 「ボンディング=トンネル経由の測定先」「単体=インターネットの測定先」のように
> configを2つ用意して使い分けるのがおすすめです(`-c` で切替)。

## 8. コマンド一覧と設定

```bash
python3 run.py                     # 引数なし: 対話メニュー(ウィザード)を起動
python3 run.py --wizard            # 対話メニューを明示的に起動
python3 run.py --duration 12       # 引数あり: 対話なしで即測定(従来どおり)
python3 run.py --per-wan           # + 回線ごとの単体測定(要 router 設定)
python3 run.py --monitor 2h        # 連続計測: 2時間、1秒ごとにCSV記録
python3 run.py --monitor 8h --no-download --no-upload   # RTTのみ長時間計測
python3 run.py --limit-mb 300      # 1方向300MBで打ち切り(従量SIM保護)
python3 run.py --no-upload         # 下りとRTTのみ(--no-download で上りとRTTのみ)
python3 run.py --samples           # 0.25秒刻みの明細CSVも保存
python3 run.py -c 現場A.yaml        # 設定ファイル指定
python3 run.py --serve             # 測定先(リフレクター)として起動
python3 run.py --demo              # ネットワーク不要の動作確認(--monitor とも併用可)
# 結果の閲覧: viewer.html をブラウザで開いて results/monitor_*.csv を読み込む
```

設定ファイルの全項目は [config.example.yaml](config.example.yaml) のコメントを参照してください。
`config.yaml` は `.gitignore` 済みです(ルーターの認証情報はコミットされません)。

## 9. 注意事項

- **データ使用量**: 例えば100Mbpsの回線を12秒×2方向測ると約300MB消費します。
  回線ごとの測定を含めるとその回線数倍になります。従量SIMでは `--limit-mb` を
  使うか、`duration` を短くしてください。
- **測定はPCの位置から**: 測定値には LAN(PC〜ルーター間)も含まれます。
  1GbEのPCで1Gbps超のボンディングは測り切れません。
- **他の通信の影響**: 測定中に配下の他の端末が通信していると、その分低く出ます。
- ルーターのCPU負荷やSpeedFusionの暗号化(AES-256)もスループット上限に影響します。

## 10. トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| 想定より大幅に遅い | PCがWi-Fi接続 → 有線に変更。他端末の通信 → 停止。`streams` を増やす(8→16) |
| 測定値が回線契約より速い | 測定経路がLAN内で完結している(測定先URLの誤り)可能性 |
| `--per-wan` で「変更権限がありません」 | Read-Onlyの認証情報。Read-Write権限のユーザー/トークンが必要([設定管理コンソールのREADME](../peplink-console/README.md#3-機器側の準備apiを使えるようにする)参照) |
| 応答をJSONとして解析できません | Router APIが無効。機器の System > Admin Security で有効化 |
| 単独測定の切替後にスキップされる | その回線が圏外・SIM未設定等で接続できていない。ダッシュボードで状態確認 |
| 社内プロキシ環境で失敗する | 既定はプロキシ不使用(直接接続)。プロキシ必須網では正確な測定はできません |
| 上りだけ極端に速い/遅い | 送信側計測のため誤差を含みます。自社リフレクター使用時はサーバー側の回線も確認 |

## 免責

本ツールは非公式のものであり、Peplink社の提供物ではありません。
`--per-wan` はルーターのWAN優先度を一時変更します。必ず本番時間帯を避け、
実行後にダッシュボードで優先度が元に戻っていることを確認してください。
